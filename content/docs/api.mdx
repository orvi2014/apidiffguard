The REST API exposes what the console shows: which endpoints you monitor, how healthy they are, and what changed when a response drifted from its baseline.

**Machine-readable spec:** [`/openapi.json`](https://apidiffguard.com/openapi.json) (OpenAPI 3.1). Point a client generator or an agent framework at it directly.

## Authentication

Create a token under **Settings → API tokens**, then send it as a bearer token:

```http
Authorization: Bearer adg_live_…
```

Tokens are shown once at creation and stored as SHA-256 hashes. Every request is scoped to the workspace the token was created in.

### Scopes

| Scope | Grants |
| --- | --- |
| `endpoints:read` | `GET /endpoints`, `GET /endpoints/:id`, `GET /diffs`, `GET /diffs/:id` |
| `endpoints:write` | `POST /endpoints` |
| `checks:run` | `POST /endpoints/:id/check` |
| `baselines:write` | Reserved — no route consumes it yet |

A token without the required scope gets `403` with the scope named in the error, so a caller can tell a permission problem from a missing resource.

`endpoints:write` is off by default. It is the only scope that can store credentials, so grant it deliberately.

### Conventions

- Enumerated values are **lowercase** (`breaking`, `bearer`, `schema`). HTTP methods stay uppercase.
- Timestamps are ISO 8601 with a UTC offset.
- List routes take `limit` (default 25, max 100) and `offset`, and return a `pagination` object with the unpaginated `total`.
- Read routes allow 120 requests per minute per workspace; `POST …/check` allows 30, because it makes an outbound request and spends check quota. Both return `429` with `Retry-After`.

## List endpoints

```bash
curl "https://apidiffguard.com/api/v1/endpoints?health=breaking" \
  -H "Authorization: Bearer adg_live_…"
```

```json
{
  "endpoints": [
    {
      "id": "…",
      "name": "List Users",
      "url": "https://api.example.com/v1/users",
      "method": "GET",
      "environment": "production",
      "tags": ["core"],
      "health": "breaking",
      "authType": "bearer",
      "diffMode": "schema",
      "baselineVersion": 3,
      "hasResponseContract": true,
      "lastCheckedAt": "2026-08-29T09:14:02.117Z",
      "responseTime": 214,
      "breakingCount": 1,
      "warningCount": 0
    }
  ],
  "pagination": { "limit": 25, "offset": 0, "total": 1 }
}
```

Filter with `health` (`healthy`, `warning`, `breaking`, `unknown`, `checking`) and `environment`.

Credentials are never returned. `authType` tells you which credential style a check uses; the secret itself is sealed and unreadable by any user-facing role.

## Register endpoints

`POST /endpoints` creates one or many endpoints, with credentials and an optional schedule. Requires `endpoints:write`.

```bash
curl -X POST "https://apidiffguard.com/api/v1/endpoints" \
  -H "Authorization: Bearer adg_live_…" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "List orders",
    "url": "https://api.example.com/v1/orders",
    "method": "GET",
    "tags": ["core"],
    "auth": { "type": "api_key", "header": "x-api-key", "key": "…" },
    "schedule": { "frequency": "DAILY" }
  }'
```

```json
{
  "endpoints": [{ "id": "…", "name": "List orders", "authType": "api_key", "…": "…" }],
  "created": 1,
  "scheduled": 1,
  "skipped": []
}
```

Send a single object, a bare array, or `{ "endpoints": [...] }` — up to **200 per request**. The route is rate-limited to 30 requests per minute, like the check route.

This is the path to use when a script or an agent needs to register an authenticated endpoint. [OpenAPI import](/docs/openapi-import) deliberately lands every endpoint as `auth_type: none`, because a spec file should never carry secrets; this route takes credentials directly and seals them per row.

### Partial success

An entry that fails validation — a missing `name`, a private-network `url`, a `bearer` auth block with no token — is returned in `skipped` with a reason, and the rest of the batch is still written. One bad row in a large import does not discard the good ones, so check `skipped` rather than assuming a `201` covered everything.

Endpoints beyond the plan's limit are reported the same way. If the workspace is already at its limit, the whole request returns `402`.

## Get one endpoint

```bash
curl "https://apidiffguard.com/api/v1/endpoints/$ENDPOINT_ID" \
  -H "Authorization: Bearer adg_live_…"
```

Returns the endpoint plus a `latestDiff` summary — `null` if it has never produced one — so "is this endpoint drifting, and what was the last damage" is a single call.

## List diffs

```bash
curl "https://apidiffguard.com/api/v1/diffs?breakingOnly=true&since=2026-08-01T00:00:00Z" \
  -H "Authorization: Bearer adg_live_…"
```

Filter with `endpointId`, `since` (ISO 8601), and `breakingOnly=true`.

## Get a diff with its changes

```bash
curl "https://apidiffguard.com/api/v1/diffs/$DIFF_ID" \
  -H "Authorization: Bearer adg_live_…"
```

```json
{
  "diff": {
    "id": "…",
    "endpointId": "…",
    "endpointName": "List Users",
    "createdAt": "2026-08-29T09:14:02.117Z",
    "accepted": false,
    "breakingCount": 1,
    "warningCount": 0,
    "infoCount": 0,
    "changeCount": 1,
    "changes": [
      {
        "id": "…",
        "path": "data.users[id=1].email",
        "type": "removed",
        "severity": "breaking",
        "message": "Field removed at data.users[id=1].email"
      }
    ]
  }
}
```

Object arrays are keyed by identity where the items carry a stable key, so `data.users[id=1]` survives reordering instead of reporting every row as changed.

Response bodies are not included. They can be large and are the part most likely to carry customer data; the change list carries the meaning.

## Run a check

```bash
curl -X POST \
  "https://apidiffguard.com/api/v1/endpoints/$ENDPOINT_ID/check" \
  -H "Authorization: Bearer adg_live_…"
```

```json
{
  "success": true,
  "diffId": "…",
  "breakingCount": 0,
  "warningCount": 1,
  "changeCount": 3,
  "alertsSent": 1
}
```

This runs the same hosted path as the console — baseline diff, schema mode, OpenAPI contract validation, and alert fan-out. `diffId` is `null` when nothing changed. A `400` means the check could not run: usually no baseline yet, or the monthly quota is spent.

## Errors

Every failure returns `{ "error": "…" }` with a status:

| Status | Meaning |
| --- | --- |
| `400` | A parameter was malformed, or the check could not run |
| `401` | No valid token or session |
| `403` | Token lacks the scope, or the role cannot run checks |
| `404` | No such resource **in this workspace** |
| `429` | Rate limited — see `Retry-After` |
